# Healz Mobile

Android mobile shell for [app.healz.ai](https://app.healz.ai), built with Expo and React Native. The app keeps the existing Healz web product inside a WebView and adds a native Android share target for sending medical documents from other apps.

## What is included

- WebView wrapper for `https://app.healz.ai`.
- WebView cookies and DOM storage enabled so the email-code session survives app restarts.
- Android back navigation through the WebView history before exiting the app.
- External web and system links (`mailto:`, `tel:`, `sms:` and similar) handed off to Android.
- Healz icon, adaptive Android icon and branded splash screen.
- Android Share target for PDF and image files from email, Gallery, Files and other apps.
- Multiple-file sharing: up to 5 files per share, with a 20 MiB total original-size limit.
- Chat picker after sharing: choose an existing Healz chat, start a new chat, refresh the list or cancel before the file is attached.
- Retry screen for network errors and a visible status while a shared document is being prepared and attached to a Healz chat.

## Document preparation

Preparation happens natively on Android before the file is passed to the WebView:

- PDFs are validated and passed through byte-for-byte. This preserves text layers, annotations and embedded scans.
- Images up to 1.5 MiB are kept unchanged.
- Larger images are decoded with EXIF orientation applied, resized to a maximum long side of 2400 px, flattened onto a white background and encoded as JPEG.
- JPEG quality is tried in descending steps of 90, 86 and 82. The first result at or below 2 MiB is used; if compression is not smaller than the source, the original is kept.
- A single shared file is limited to 12 MiB before preparation.

This is intentionally conservative: medical text and numbers are more important than achieving the smallest possible upload.

## Requirements

- Node.js 20+ recommended.
- JDK 17, 21 or 25 for a local Android release build. The build script prefers Homebrew JDK 21 and supports the JDK 25 bundled with Android Studio.
- Android SDK with `ANDROID_HOME` configured.
- Android device or emulator for testing.

## Install and run

```bash
npm install
npm start
```

For a local native Android run:

```bash
npm run android
```

The native share target is generated by the Expo config plugin during prebuild. If the Android folder is absent, `expo run:android` generates it automatically.

## Verify the project

```bash
npm run typecheck
npm run doctor
npm run verify
```

The verification script checks the app configuration, branded assets, URL scheme, TypeScript and Expo diagnostics.

## Build an installable APK

```bash
npm run build:android:release
```

The script selects a supported local JDK, runs Expo prebuild and assembles a release APK. The result is written to:

```text
android/app/build/outputs/apk/release/app-release.apk
```

The `android/` directory is generated locally and intentionally ignored by Git. The source of its native share integration is kept in `plugins/`.

## QA checklist

The manual smoke-test checklist is in [`docs/shell-qa-checklist.md`](docs/shell-qa-checklist.md). At minimum, test:

1. Email-code login.
2. Force-close and reopen with the session preserved.
3. Android back navigation.
4. Opening an external link and returning to Healz.
5. Sharing one PDF/image and multiple files from another app.
6. Selecting an existing chat or starting a new chat before the file is attached.
7. Cancelling the chat picker and retrying the chat list.
8. A large image, a small image and a PDF.
9. Offline/retry behavior.


## Scope and limitations

This project wraps the public Healz website and does not modify the Healz web product. It adds a small native chat-picker surface only for the Android share flow; chat contents and file upload remain in the WebView. The current native document import path is Android-specific because the requested deliverable is a directly installable Android APK. The shared TypeScript/React Native shell remains suitable for an eventual iOS implementation, where the share extension would need a separate native integration.
